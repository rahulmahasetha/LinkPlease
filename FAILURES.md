# Failures

1. **Webhook Event Loss on Restart**: When a webhook is received, we immediately write the `event_id` to the database (to prevent duplicate processing) and place the payload into an in-memory `asyncio.Queue` before returning 200 OK. If the application crashes or is restarted before the background worker processes that queue item, the event is permanently lost. Redelivery won't save us because the `event_id` was already saved as processed.
2. **Head-of-Line Blocking on 500 Errors**: Our DM sender worker queries the database for `status = 'queued' AND external_dm_id IS NULL LIMIT 1`. If the external API returns a 500 Internal Error, the worker leaves the status as `queued` to retry it later. However, because we don't implement backoff or skip to the next row, the worker will repeatedly try to send that exact same DM, blocking all other queued DMs until it succeeds.
3. **No Retries for Asynchronous Failures**: While we successfully poll the `/v1/dm/{dm_id}` endpoint to track delivery status, if a DM is eventually marked as `failed` by the external API, we simply update our database status to `failed` and give up. We do not attempt to re-queue or retry these asynchronously failed DMs.
4. **Late Deletions**: If a `comment.deleted` event arrives after we've already received a 202 Accepted from the `/v1/dm/send` endpoint, we have no mechanism to cancel the DM on the mock API's side. The DM will still be delivered even though the comment was deleted.
